# Task contract: Issue #337 admitted finite MCP response drain

## Outcome

Stopping or replacing the MCP runtime cannot truncate an already admitted finite JSON-RPC response. Shutdown closes new admission, lets finite requests finish through the existing response-end acknowledgement, then closes sessions, connections, and the event-loop group.

## Owners and invariants

- `MCPHTTPNetworkResourceOwner.RequestOperation` is the single owner of request work, domain work, response-end state, and the shutdown disposition.
- A request starts closeable. After a complete body is classified by the existing `responseSourceKind(for:)` as non-null-id JSON-RPC, it may be promoted once to finite-drain ownership under the request owner lock.
- Classification versus shutdown has one linearization point: promotion first means drain; draining first means the still-unclassified request is closeable.
- During drain, no new connection/request is admitted. An already promoted finite operation may still bind its session and start/finish its own domain work; unrelated or newly admitted work may not.
- Finite ownership lasts through HTTP work completion, empty domain work, and the existing response-end acknowledgement. Do not invent another ACK, timer, polling loop, or server-side mirror dictionary.
- Open SSE, notifications/null-id requests, rejected bodies, and incomplete bodies are closeable during drain.
- Peer close or transport failure escalates a draining finite request to destructive close; it must not wait for a response to a vanished peer.
- Connection close is signalled exactly once when its drainable requests retire. Generation close completes only after connection close acknowledgement.
- Session teardown and event-loop shutdown happen after the network drain, so they cannot disconnect the source transport of a finite response.

## Intended state transition

```text
accepting -> admissionClosed/draining
  closeable requests: cancel
  finite requests: handler -> domain work -> writer .end -> response-end ACK
draining -> closing(serverStop) when requests are empty
closing -> closed after channel close acknowledgement
```

Use explicit draining cases/dispositions on the existing owner types rather than boolean flags. Preserve fail-fast checks for impossible owner misuse, and revalidate state after suspension.
